# 발음 인식 입력 점검 — 2026-11-10

현재 발음 훈련에서는 RNNoise·libfvad를 건너뛰고 원본 녹음을 기존 FIR로 16kHz 변환한다. 음량 측정·높낮이 연습의 소음 억제·발화 감지는 유지한다. 아래 입력·디코더 실험은 이 변경 전의 기록이다. 현재 경로는 [녹음 처리 문서](practice-audio-processing.md)에 정리했다.

사용자가 보고한 예시는 `앞으로 → 압드으로`다. 이번 변경은 비교 표시가 아니라 모델 앞의 녹음·재표본화 경로를 대상으로 한다. `비슷함`과 기존 비교 규칙은 유지한다.

## 적용한 수정

- 웹 48→16kHz 변환에 Android와 동일한 63tap centered Hamming FIR을 적용했다. 로컬 Chrome 156에서 기존 변환은 9kHz를 7kHz로, 12kHz를 4kHz로 진폭을 유지한 채 접어 넣었다. 수정 후 두 시험 신호의 감쇠는 각각 58.85dB와 60.14dB다. 0.5~6kHz 시험 신호의 손실은 0.06dB 이내다.
- FIR의 지연을 보상하고 부분 프레임의 마지막 입력을 보존한다. 동일 PCM16 입력 27개에서 실제 Kotlin 출력과 JS 출력 895,583개 샘플 및 SHA-256이 모두 일치했다. 이 검사는 음소 인식률 평가와 별개다.
- Android 녹음 source를 `DEFAULT`에서 `VOICE_RECOGNITION`으로 명시했다. Galaxy Jump2의 기존 녹음 로그에는 `MIC`가 사용됐다. 기존 음량 엔진도 미가공 입력을 지원하지 않는 기기에서 이 source를 사용한다. Bluetooth·입력 기기 선택과 앱의 RNNoise·VAD 처리는 유지한다.

[Android 공식 문서](https://developer.android.com/media/platform/mediarecorder#creating_and_running_a_mediarecorder)는 미가공 입력을 지원하지 않을 때 AGC·소음 억제를 사용하지 않는 `VOICE_RECOGNITION`을 권한다. 이것이 해당 사용자 오인식의 원인이었다거나 설정 변경만으로 인식률이 얼마나 개선됐다고 단정하지 않는다. 실제 source 적용과 발음 결과를 구분해 확인한다.

## 실제 모델 비교에서 채택하지 않은 후보

고정된 기존 IPA 모델·greedy CTC에 실제 Seoul Corpus 발화 70개를 사용했다. 기존 개발30과 검증40을 재사용한 비교이며 새 독립 임상 평가가 아니다. 평가 단위는 기존 공통 자모 매핑의 음소 대치·삭제·삽입 수다. 원문을 모델이나 디코더에 입력하지 않았고 음성을 서버로 전송하지 않았다.

| 후보 | 개발30 | 검증40 | 판단 |
| --- | --- | --- | --- |
| 현재 full RNNoise | 157/818 | 180/1269 | 기준 |
| raw 75% + RNNoise 25% | 159/818 | 개발 단계에서 탈락 | 미채택 |
| 제한적 증폭, 원래 음량 | 152/818 | 182/1269 | 검증에서 악화해 미채택 |
| 제한적 증폭, 원본 음량 0.25배 후 녹음 처리 | 166→155/818 | 181→178/1269 | 원래 음량의 악화를 상쇄하는 일반 개선으로 해석하지 않는다. |
| CTC prefix beam 8 | 158/818 | 개발 단계에서 탈락 | 미채택 |

증폭 후보는 원본 입력의 분산 검사 후 최대 4배·RMS 0.1·peak 0.95로 제한하고 추가 상수를 탐색하지 않았다. 같은 검증 음성 8개에 합성 백색잡음을 더한 진단에서는 오류가 128→129/243으로 늘었다. 잡음만 있는 3초 입력의 비공백 음소도 5→6개로 늘어 제품에 적용하지 않았다. 정상 음성 0.25배 실험은 통제된 음량 변환이며 실제 휴대폰 녹음을 대신하지 않는다.

실험 원본은 `.local/recognition-input-eval-20261110/`, 디코더 비교는 `.local/recognition-decoder-eval-20261110/`, 웹 DSP 재현은 `.local/web-input-audit-20261110/`에 있다. 계획·입력·출력·logits 해시와 제품 입력 거절 여부를 보존했다. 실패한 후보 코드와 임계값은 제품에 남기지 않았다.

## 후속 음소 디코딩 보정

새 입력 경로에서 사용자가 세 번 읽은 결과는 `아프로`, `아프으로`, `아프스록`이었다. 기기 녹음 로그의 실제 source가 `VOICE_RECOGNITION`으로 바뀐 것은 확인했지만 추가 음소는 남았다.

모델의 비발화 blank logit에 고정 0.5를 더해 약한 비공백 후보가 불필요하게 선택되는 횟수를 줄였다. 이후 동일한 IPA 모음 사이에 정확히 한 blank 프레임만 있을 때 이어진 모음으로 처리한다. 자음·다른 모음·미확인 음소·공백·2프레임 이상의 blank는 이 병합을 적용하지 않는다. 선택 문장은 디코딩에 사용하지 않는다.

| 기존 greedy 대비 | 전체 오류 | 대치 | 삭제 | 삽입 | 자음 삭제 |
| --- | --- | --- | --- | --- | --- |
| 개발30 / 818음소 | 157→150 | 75→74 | 13→14 | 69→62 | 8→8 |
| 기존 검증40 / 1269음소 | 180→172 | 93→93 | 19→21 | 68→58 | 14→15 |

같은 코퍼스를 여러 후보 검토에 재사용한 탐색 결과다. 40개 표본의 공통 자모 음소 오류율은 14.18%→13.55%이며 새 독립 검증으로 부르지 않는다. 삽입이 줄었지만 일부 끝 음소 누락은 늘었다. 잡음 전용 진단도 잘못된 음소가 5→4개로 줄었을 뿐 제거되지는 않았다. 짧은 실제 모음 단절이 한 프레임인 경우와 이어진 모음을 구분하는 평가는 별도다.

웹·Android 제품 디코더는 저장된 70개 logits에서 고정 결합 후보의 결과와 모두 일치했다. 계획 해시는 `961c14d5fb95da0573811a60757fa15a8af94c7f54b4f9c5691717bdf2d27d78`이며 세부 행은 `.local/recognition-decoder-eval-20261110/combo05-gap1/`에 있다. 후속 사용자 보고는 `아프으로`, `아프으로`, `아크로`로, 해당 보정만으로 문제가 해결되지 않았다.
